# 2. Web-first with Capacitor, not a native engine

Date: 2026-09-18

## Status

Accepted

## Context

The game must ship to web, Android and iOS. Its two hard requirements are real-time microphone analysis and real-time spectral analysis of playing audio, plus flat vector rendering at 60fps on a phone.

Options considered:

**Unity / Godot.** Strong engines, and Godot exports to all three targets. But both treat the web as a secondary export: Unity's WebGL builds are large and start slowly, and Godot 4's web export still has caveats around audio input. Both would also mean doing DSP in C#/GDScript and re-solving problems the Web Audio API already answers.

**Flutter + Flame.** One codebase across all three, but audio capture and analysis are plugin territory on every platform, including web — the exact part of this project that is hardest and most platform-specific.

**Web-first, wrapped with Capacitor.** The Web Audio API is the best-supported real-time audio stack on all three targets and is _the same API_ on all three. Canvas/WebGL rendering of flat vector shapes is cheap. Capacitor wraps the same bundle into Android and iOS shells and provides a native plugin path for the one thing the web cannot do (Android system audio capture).

## Decision

TypeScript + Vite + PixiJS for the app, Capacitor for the Android and iOS shells.

PixiJS over Phaser because the game needs a renderer, not an engine: the physics here is gravity and AABB overlap, and the stage generator is bespoke. Phaser's scene/physics/loader machinery would be carried without being used.

TypeScript is pinned to 6.0.3 rather than the current 7.0.2 because `typescript-eslint` still declares `typescript <6.1.0`. Type-aware linting is worth more here than being on the newest compiler; see `docs/roadmap.md`.

## Consequences

One codebase, one audio API, one renderer. Web is a first-class target rather than a degraded export.

The cost is that anything the web platform cannot do needs a Capacitor plugin written per platform — currently just Android playback capture. It also means accepting webview performance characteristics, which is fine for flat vector shapes but would not be for a heavy 3D game.

Native projects (`android/`, `ios/`) are generated by `cap add` and gitignored, so permission entries in `AndroidManifest.xml` and `Info.plist` must be re-applied after a fresh generate. `docs/platforms.md` records exactly what to add.
